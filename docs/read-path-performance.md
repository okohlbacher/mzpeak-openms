# Phase 0 — baseline and diagnosis

Machine: Apple Silicon, macOS 26.5.1, Arrow/Parquet 25.0.0, meson `release`
build, files on local SSD. Every number is single-threaded wall clock from
`mzp-bench`, with peak RSS from `getrusage`.

## Fixtures

Generated by this project's own writer, which bounds row groups at `1 << 20`
rows — the same bound the real files use.

| fixture | spectra | points/spectrum | rows | row groups | rows/group |
|---|---:|---:|---:|---:|---:|
| `run2k` | 2,000 | 1,627 | 3,254,000 | 4 | 1,048,576 |
| `run13k` | 13,009 | 1,627 | 21,165,643 | 21 | 1,048,576 |
| `run2k-manygroups` | 2,000 | 1,627 | 3,254,000 | **326** | 10,000 |

`run13k` reproduces the reported `12_80` shape almost exactly: 21 row groups,
and **20 of 21 groups begin with a spectrum that started in the previous
group** — the straddle property the handoff warns about, reproduced.

`run2k-manygroups` is `run2k`'s bytes rewritten with small row groups. It is
the only way to reach the row-group *count* of a Bruker diaPASEF file (3,518)
without a 70 GB fixture.

## Where the time goes

`sample(1)` on the forward pass, 4,232 samples, all on the main thread.
`Spectrum::mz()` accounts for all of them; `Signals::select` for 4,213.

| | samples | share of `select` |
|---|---:|---:|
| Parquet decode (`GetRecordBatchReader` + `ReadNext`), ZSTD-dominated | 3,723 | **88%** |
| `Query::eval` — the per-row predicate in `Executor::Impl::filter` | 384 | 9% |
| allocation and misc | ~104 | 3% |
| `Planner::plan()` | ~0 | ~0% |

## The controlled experiment

Same 3.25 M rows, same values, only the row-group size differs:

| row groups | rows/group | ms/spectrum |
|---:|---:|---:|
| 4 | 1,048,576 | 19.55 |
| 326 | 10,000 | **1.83** |

Per-spectrum cost tracks row-group *size*, which is what "decodes a whole row
group per spectrum" predicts and what nothing else does. The diagnosis in the
handoff is confirmed, by mechanism and not only by magnitude.

## What the numbers say about the plan

1. **88% is the redundant whole-row-group decode.** A row-group cache removes
   it. On `run13k` that is 21 decodes instead of 13,009.

2. **The planner is free at 21 row groups and expensive at 326.** Fitting the
   two-point experiment gives roughly 5 µs per row group per spectrum, which is
   0.1 ms at 21 groups and would be **~18 ms/spectrum at a diaPASEF file's
   3,518 groups** — on its own, before any decode. This is invisible in the
   handoff's measurements and is the reason Phase 1 exists.

3. **A cache alone is not enough.** The 9% per-row predicate is O(rows in the
   page range), not O(rows in the spectrum). With 1 MB pages that is ~131 k
   rows evaluated to extract ~1,627.

4. **Projected after Phases 1–3:** the Arrow floor is 0.315 s for `run13k`.
   Adding per-spectrum work that is proportional to the spectrum rather than to
   the page, a full forward pass should land near 0.4–0.6 s, against mzML's
   3.55 s for a comparable run.

# Phase 1 — hoist per-row-group statistics out of the per-spectrum path

`Planner::plan()` consults every row group on every query. Each visit built a
`RowGroupMetaData`, a `ColumnChunkMetaData` and a `Statistics` from the file
metadata, and — worse — obtained that row group's *page index* before the
statistics had a chance to reject it.

Two changes:

- `StatsIndex` (`include/mzpeak/util/planner.h`) caches per-(row group, column)
  statistics for the lifetime of the open file, and is shared by every planner
  over that file. Absence is cached too, so a column without statistics is not
  re-examined once per query forever.
- `plan_row_group` evaluates statistics **first** and returns before touching
  the page index. Selecting one spectrum rejects all but one or two row groups,
  and reading thousands of page indexes only to discard them was the bulk of
  planning on a file with many row groups.

## Result

Three runs each, 200 spectra, same fixtures:

| fixture | row groups | before | after | change |
|---|---:|---:|---:|---:|
| `run2k-manygroups` | 326 | 1.861 ms/spectrum | **1.331 ms/spectrum** | −28.5% |
| `run13k` | 21 | 19.66 ms/spectrum | 19.49 ms/spectrum | within noise |

The saving is 0.53 ms spread over 326 row groups: **~1.6 µs per row group per
spectrum**. That is why it is invisible at 21 groups and worth ~5.7 ms/spectrum
on a 3,518-group Bruker diaPASEF run.

This phase deliberately does **not** touch the dominant cost — the whole
row-group decode per spectrum, which is Phase 2.

# What the Phase 0 harness does NOT establish

An adversarial review (Codex, plus an independent Kimi run that reproduced the
baseline and built its own many-row-group fixture) attacked the measurements
above. These are the limits that survived checking. They are recorded because
the projection in Phase 0 is weaker than it first reads.

**The 0.4–0.6 s projection was optimistic; 1.0–1.5 s is defensible.** The
profile shows `Signals::select` is 99.6% of a forward pass, so the 88% figure
does carry over to total time (87.6%). But the ~0.4% that is *not* `select` —
the point decoder's per-element copies — is 0.05 ms/spectrum, i.e. **0.64 s
over `run13k` on its own**, on top of the 0.315 s Arrow floor. Caching cannot
remove it.

**The synthetic fixture has no nulls, so null marking is unexercised.** The
bundled `small.mzpeak` carries 39,968 nulls in each signal column — 18.4% of
rows. Null reconstruction runs *after* `select` and survives every phase
planned here. It is also boundary-sensitive: reconstruction must see the whole
assembled entity, which is why `encoding.h` concatenates before filling.

**Nor does it exercise the chunked or Numpress layouts**, whose per-chunk
copies are O(points) and likewise survive row-group reuse. The writer is
point-only.

**Nor absent statistics or page indexes.** The writer always emits both. A
producer that emits neither makes the planner fall back to a full scan of
*every* row group for a single spectrum.

**Page geometry is a producer choice and moves the residual predicate cost by
orders of magnitude.** Arrow 25 defaults to 20,000 rows per page; a producer
writing one page per row group would make the per-row predicate evaluate
1,048,576 rows per spectrum instead of 20,000. The measured 9% is not portable.

**A spectrum larger than a row group defeats cache reuse.** At 1,627 points no
spectrum spans more than two groups. A diaPASEF frame of 2 M points spans
three, and each is decoded for exactly one spectrum — the Phase 2 cache buys
nothing there beyond the shared boundary groups.

**Timers exclude `open()`.** In particular the "metadata pass" number times
13,009 lookups into an already-built map, not reading 13,009 metadata rows;
`Spectra` reads the whole metadata model in its constructor.

**The Arrow floor uses a different I/O path** (`arrow::io::ReadableFile`) than
the reader (a custom adapter, or `zip_fseek` for archives), and every mode runs
once with no warm-up. It is a floor for a warm unpacked directory, not for a
cold archive.

## Gates, restated

`checksum` now hashes the mobility array as well, and runs the same pass a
second time through `get_spectra_batch`, failing if the two digests differ —
without that, a stitching defect that only the batch path had would leave the
digest untouched.

| fixture | peaks | digest | scalar | batch |
|---|---:|---|---:|---:|
| `run2k` | 3,254,000 | `9fae6e76aea6a57e` | 38.3 s | 38.1 s |
| `run13k` | 21,165,643 | `5604ebcf86dd4567` | 251.8 s | 252.5 s |

(The earlier `3fba0c5528aac85a` / `841dd2473d045f35` predate mobility being
hashed.)

Peak RSS differs between the two passes -- 58.6 MB scalar against 80.8 MB
batched on `run13k` -- because `get_spectra_batch` holds 512 decoded spectra at
once where the forward pass holds one.  That gap is the number to watch in
Phase 3: a batched reader that hands out views into a decoded row group should
move it, and a batched reader that quietly accumulates whole row groups will
move it a great deal.
